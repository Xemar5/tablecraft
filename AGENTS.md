# Agent instructions

## Project

Tablecraft is a local-first, 2D board-game design and playtesting app. It uses React, TypeScript, Vite, Zod and SpaceTimeDB 2.15. Read the [README](README.md) when you need the full setup guide, user workflows, or product details.

## Setup and validation

- Use a supported Node version: Node 22.23.4+, 24.22.1+, or 26.12.1+.
- Install frontend dependencies with `npm ci`; start the app with `npm run dev`.
- Run `npm test` and `npm run build` for routine validation.
- CLI changes also require `npm run cli:check`; exercise the CLI through `npm run cli -- --help` and focused command tests.
- Browser tests require Chromium (`npx playwright install chromium`), a running local SpaceTimeDB server and a published module (`npm run test:e2e`).
- Check server types with `npx tsc -p server/tsconfig.json`. Shared command changes also require republishing the module before live clients can use them, even if the database schema and generated bindings are unchanged.
- For multiplayer changes, run `npm run db:generate` after changing the module schema, then publish with `npm run db:publish`. Do not use anonymous publishing for a database that must be updated later.

## Architecture

- `src/domain.ts` is the authoritative shared contract: Zod schemas, project invariants, and immutable game commands are used by both the browser and server.
- `src/Designer.tsx` and `src/ComponentView.tsx` implement component editing and rendering. Editing chrome that must keep a constant screen size (path anchors/handles, the pen tool's preview) is drawn by `PathOverlay` in screen space using the path SVG's `getScreenCTM()`, never inside the zoomed face; selection outlines use a `box-shadow` divided by the zoom (outline widths round up to 1px before zooming). Drags and resizes snap with `zoomPrecision(zoom)`/`snapTo` from `src/designTransform.ts`. `convertToPaths` (`src/designerOperations.ts`) flattens shapes exactly (`shapeAsPath`) and boolean groups through `compoundRings`. A `component` layer may have no `componentId` yet (it renders a placeholder) but a set id must exist. `src/vectorGeometry.ts` computes SVG path and live boolean-compound geometry; keep the source shapes editable in the layer tree. Nested component nodes hold live component-ID references and render against the full project catalog on every surface.
- Locks: `locked` (a piece's own, or a locked group's through `withGroupLocks`) holds a piece in place on the table; `orderLocked` (a piece's own, or an order-locked group's, see `groupOrderLocked`) keeps its place in the hierarchy. Table commands that reorder or regroup pieces or groups call `keepOrder` first, and `front` (the raise on pick-up) skips order-locked pieces.
- Grids: `src/grids.ts` holds table grids and the grids components carry (`Component.grids`, in component coordinates, inside `bounds`). Snapping, snap detection, `snapTo` and the scripting grid API go through `placedGrids` (carried grids of table pieces first, topmost first, then table grids; keys are grid ids or `piece id/grid id`), never `projectGrids` alone. `GridEditor` edits both lists through `GridActions`; `ComponentGridCanvas` edits a component's grid on the designer canvas.
- Layer placement: `src/layoutRules.ts` decides per axis which of X/Y, Width/Height and margins apply and which sizings a layer may use (`sizingUnavailable`, shown grayed out with its reason). X/Y place the layer's pivot (`pivotX`/`pivotY`, fractions of its size); it turns about the pivot and grows around it. Map points and boxes with `toParent`/`fromParent`/`parentBounds`/`reboxed`/`repivoted` from `src/layerGeometry.ts`, never with centre-based math. `withPivot` (run by the layer schema and `makeNode`) gives a layer without a pivot the one that keeps it where it was (top-left, or the centre with X/Y moved there when it is turned), so every layer has one. Auto font size (`autoFontSize`, `minFontSize`) is measured in the page by `FitText` in `src/ComponentView.tsx`.
- Wildwood (`src/wildwood.ts`) is the sample a new workspace starts with and a showcase of the app: when you add a user-facing feature, add a small use of it to Wildwood (and its Wanderer's guide pages) in the same change. Its card, token, board and dice are also the **Add component** templates, which draw the art in (`artLayer` without an art id) so a template adds no other component. Keep it free of duplicate components: its botanical art is one artwork component with fern/moon/sun variants, linked with `nestedFit: 'contain'`. Unit tests that need a plain table use `starterTable()` from `tests/fixtures.ts`, not the sample, so the sample can grow freely.
- Wildwood's botanical artwork is an ordinary linked vector component, with generic CSV-driven layer visibility. `upgradeLegacyArtworkProject` in `src/templates.ts` deterministically upgrades legacy shape-text artwork, preserving its original shape; run it at persistence and authoritative room boundaries before validation, and reject over-limit upgrades without overwriting the original. Template consumers must add the full dependency-first `templateBundle` closure.
- `src/Playground.tsx` implements the table, pieces, stacks, hands and seats; `src/PlaygroundPieces.tsx` lists table pieces (not held ones) for selection inside nestable Pieces-panel groups, planned by `src/pieceGroups.ts`. Groups live in `project.groups` (absent when there are none) and `instance.group`, change only through the shared `createGroup`/`renameGroup`/`ungroup`/`moveToGroup` commands, and are normalized at the end of every `applyCommand`: held pieces leave groups, a stack shares its bottom piece's group, empty groups are removed. History entries record groups so undo restores them. G/Shift+G group only while the pointer is over the Pieces panel; elsewhere G stacks.
- Books (`kind: 'book'`) and dice keep their pages/faces as CSV rows of one piece (`hasPages`): they never spawn per-row variants, and `cycleVariant` turns pages (clamped) or steps faces (looped).
- `src/uiScale.ts` scales the whole page with CSS `zoom` on the root. Pointer coordinates and bounding rects are viewport pixels while style lengths are page CSS pixels, so convert with `cssPx()` whenever a pointer delta or client position becomes a style, pan or design length (hit tests and rect comparisons stay in viewport pixels). Viewport units in CSS are zoomed too; divide them by `var(--ui-scale,1)`. The app shell fills `html/body/#root` at 100% height and must never need page scrolling.
- `src/settings.ts` stores per-browser user settings (profile, server defaults, theme). `src/darkTheme.ts` is a PostCSS plugin that derives night mode from the light stylesheet, so style new UI in `styles.css` (not inline colors); mark elements that must keep light colors with `[data-theme-fixed]`. New dialogs should follow the existing modal card style (Lora headings, icon tiles, soft cards).
- `src/App.tsx` coordinates projects, persistence, commands and navigation. `src/storage.ts` validates internal JSON and local saves; `src/portable.ts` owns ZIP-only project/component files (`project.json` plus binary `assets/`). `src/assets.ts` imports files; assets live on non-spawnable texture/font components, and design nodes reference their IDs. Include asset dependencies when bundling/remapping/linking components (`namedAssetReferences` adds assets picked by name); deleting an asset clears its consumers. Image and text layers also pick textures/fonts by (bound) name through `resolveImage`/`resolveFontFamily`, so local asset names are unique case-insensitively: `component`/`addComponents` reject duplicates, and import paths rename with `withUniqueAssetNames` first. Keep browser font registration in `src/AssetInspector.tsx` synchronized with the current catalog.
- Designer edits do not dispatch per change: `App.tsx` keeps them in a draft (`src/designDraft.ts`) checked by `validateComponentEdit` (the `component` command's own checks plus component validation, without parsing the project or its asset data). The app renders the project with the draft applied; the draft commits as ordinary `component` commands when the designer is left (playground, Home, another project) and before any other dispatch, so commands keep their order. Before that, `Designer` itself holds continuous edits (an edit session: color pickers, scrubbing, sliders, typing, held nudges) for 200 ms after the last tick or until the session ends, showing them locally; `flushRef` lets `App.dispatch` hand a held edit over first, and unmounting or hiding the page flushes it. Discrete edits flush any held edit and go out at once. Each pending edit is a state the designer really had, so replaying edits in order is valid at every step; keep page/face removals as separate steps. The draft is stored under its own localStorage key right after changes (throttled) and on page hide, recovered on boot, and cleared only once the committed archive has been saved.
- `src/panelLayout.tsx` manages browser-local panel-size preferences and accessible splitters; viewport constraints must leave room for the canvas. Inspector tab selection lives in `App` so keyed Designer remounts retain presentation state without retaining edit history. These preferences are not project or multiplayer state.
- `scripts/tablecraft.ts` exposes validated offline generation and project commands; `scripts/live.ts` uses the generated client and authenticated reducers. Keep CLI identity files outside the repository and report partial live batches explicitly.
- `src/multiplayer.ts` and generated `src/module_bindings/` connect clients to the SpaceTimeDB module in `server/src/index.ts`.
- Live commands are predicted in `App.tsx`: each pending dispatch or seat claim is reapplied over the confirmed room state with `applyCommand` and dropped when its reducer settles. The SDK applies room updates before the reducer promise resolves, so this never double-applies. Keep commands deterministic (client IDs and seeds) so predictions match the server.
- Scripting (`src/scripting.ts`): the exported `applyCommand` is `runCommand` around `applyTableCommand` (the table engine). `call`/`tick`/script changes run Lua in a fresh Fengari state per run (scripts loaded in order, globals not kept; `memory` and the table are the only state), and other commands run the scripts' event handlers detected by diffing before/after. Script actions go through `applyTableCommand` with no actor (or the hand's seat for hand commands), so they follow locks and hand permissions and never trigger events. Runs must stay deterministic (seeded `math.random`, command-derived ids and seeds, no clock/IO/`load`) because the server and every predicting client replay them; failures never throw out of `call`/handlers but log to `project.scriptLog` and keep the table unchanged. A run's undo base (`undoBaseOf`) carries `game.beginNoUndo()` changes; `applyPlaygroundCommand` records it instead of the previous state and skips entries when nothing undoable changed. `src/vendor/fengari.js` is generated by `npm run vendor:fengari` (the SpaceTimeDB bundler can't resolve Fengari's Node-only requires); don't edit it by hand. The server only accepts script changes from the host unless `settings.scriptEditing`, rejects client `tick`s, and runs `update(dt)` from the scheduled `room_tick` table (kept in sync by `syncUpdates`) while a room member is connected.
- `src/playgroundHistory.ts` wraps shared commands with bounded tabletop undo and redo: undo pushes a snapshot of the current table onto `redo` (restored by `redoPlayground`, which pushes back onto `entries`), and any command that records a new entry drops `redo`. Offline archive/history updates must be atomic; multiplayer history lives only in the private `playground_history` table and reducers serialize dispatch/undo/redo (`historyStep` in the server). The room view exposes only the undo and redo counts and the invalidation notice. Never accept client history or restore saved designs, seat identities or ownership. Component edits/removal and explicit seat creation clear history; joining an existing room does not.
- Keep offline and multiplayer behavior consistent by routing mutations through `applyCommand` and the shared command schema; put multiplayer authority checks in server reducers as well.
- Stacking order: table z-order is `instances` array order (boards always render underneath). The `zOrder` command and the designer's `reorderLayers` both use `reorder` from `src/zOrder.ts`; table steps only pass overlapping pieces (stacks move as one unit), layer steps pass the next sibling. The Pieces panel's `arrangePieces` command regroups rows and moves them (a group with all its subgroups' pieces) as one contiguous block of units just above or below a target row's pieces; both commands share `tableUnits()` in `applyCommand`. After order and grouping commands, `gatherGroups()` keeps each group's units contiguous (each group, and each subgroup inside its parent, sits at its topmost piece), which is exactly the Pieces panel's order; so a `front` on a grouped piece raises its whole group. Persistent stacks are `project.stacks` records (`persistentStackSchema`): their pieces keep the record's id in `stack`, single-piece stacks with it don't dissolve, `keepPersistentStacks()` re-labels merged stacks (merges mint new ids) back to the persistent id, `syncPersistentStacks()` keeps records at their bottom piece, and `fitsPersistentStack()` decides who may join by the record's tag. A group's own `locked` flag holds its pieces (and subgroups) in place without touching their `locked` flags: reducers check `isLocked()` (own or group lock) and `Playground` works from `withGroupLocks(project)`, using the saved flag only for a piece's own Lock toggle.
- Large projects rely on structural sharing: non-design commands, undo and room updates reuse the previous `components` array and objects, `validateProject` skips arrays it already validated, and `ComponentView` is memoized. Never mutate component objects in place; replace them immutably.
- On large tables any inline style or layout change triggers page-wide compositor layerization. The table camera and the dragged pieces/overlays move with persistent Web Animations (`useCompositedTransform` in `src/Playground.tsx`); never set the camera transform or per-move drag positions inline. Table pieces are memoized `TablePiece` components with stable `pieceEvents` handlers, and the zoom label is throttled.
- Fullscreen piece previews are local presentation state (`src/PiecePreview.tsx`, `src/playgroundPreview.ts`), not commands. The preview's pan is derived from the latest pointer position, zoom, rotation and the space between its title and help bars, and is applied straight to its compositor animation; recompute it whenever any of those change. Re-evaluate face visibility against the current actor and hand privacy while open, and isolate preview shortcuts from table/global actions. Independent grid snaps use atomic `transform.positions`, which must cover exactly the selection and preserve complete stacks.

## Invariants and trust boundaries

- Validate imported data, project state and commands at their boundaries. Preserve unique IDs, valid layer-parent trees, component/player references, and compatible stack membership.
- `validateProject` also owns nested-component reference/cycle/depth checks, nested data-row bounds, and vector-compound source invariants. Component JSON exports include their linked dependency closure; imports remap those IDs and insert dependencies before parents. Keep missing or invalid parent-field row indices explicit in rendered output—never silently fall back.
- Instances reference component IDs and CSV row indices. Keep that relationship so design and CSV updates refresh all spawned, stacked and held pieces.
- Grids (`src/grids.ts`): `project.grids` lists grid layers in priority order (absent: one legacy square grid from `settings.grid/snap/gridSize/gridOffsetX/Y`, see `projectGrids`; the `grid`/`removeGrid`/`reorderGrids` commands materialize it). Square point ids are `"col,row"`, hex ids axial `"q,r"`, points grids their own ids. Snapping is authoritative in the shared engine: moves with `snap: true` (transform, release, releaseMany, playVisibleHand, extractMove) run `snapTarget()` per unit (a stack goes by its bottom piece), and `snapTo` puts pieces on a named point; forced rotations come from the point, then the grid. Which grids take a component uses the tag filters below on `gridTags` (untagged components match every grid; `snapToGrid: false` opts out). Snap state is derived from positions (`snapOf`, within 0.01px), never stored. Undo entries record grids (null for the legacy grid).
- Stack tags and filters (`src/tags.ts`): components list `stackTags` (plus the legacy single `stackTag`, read by `componentTags()`). A filter is DNF (`anyOf` rules of `has`/`lacks` tags, compared case-insensitively); untagged components fit every filter and a rule-less filter takes anything. New stacks get `newStackFilter()` (the tags their pieces share; tagged pieces sharing none can't stack, see `canStack`). Ordinary stacks store the filter on every member (`stackFilter`, unified to the bottom piece by `normalizeStackFilters`, so merges keep the target's); persistent stacks store it on their record (legacy `tag` read as a one-tag filter). `stackFilterOf()` resolves a stack's filter (deriving one for stacks from before filters) and `stackJoinError()` is the shared joining check; filters gate joining only, never existing membership.
- Turning off hand, flipping or stacking support must keep existing instances valid. Do not silently discard player-held pieces when hands are hidden.
- Multiplayer rooms are for trusted playtesters. Hidden hand faces are **visual privacy only**: subscribed clients receive the complete room state. Room codes grant editing access. Never describe this setup as competitive secrecy.
- Associate remote seat changes and private hand actions with the authenticated sender; do not trust a client-supplied player ID as proof of ownership. Each player owns `allowHandInsert` (default on) and `allowHandTake` (default off) for their hand; In multiplayer, `handSettings` requires the authenticated sender to own that seat, or for it to be empty, or to be the room host. Fall back to legacy table permission fields for older saves only; table settings commands cannot change them. Visible-hand commands check each source hand's taking permission and the destination hand's insertion permission independently, and indexed transfers insert atomically using instance `order`. Hand permissions stay outside shared tabletop undo. Ordinary hand commands retain their ownership checks. The identity that creates a room is recorded in the private `room_host` table; the host may change other seats' settings and remove them (`player`, `handSettings`, `removePlayer`) but never change a seat's `owner` or act from another player's hand, and the UI marks these host overrides in red. Offline, the active player may edit every hotseat seat; the UI marks these as hotseat overrides. Online, each identity occupies at most one seat (`owner` is the identity hex, `''` marks an empty seat). Hosting empties every seat except the host's; `join_room` never creates seats; `take_seat` claims an empty or new seat (or `''` to watch) and releases the sender's others; disconnecting the identity's last connection (tracked in private `live_connection`) releases its seat. Seatless viewers may dispatch only design commands (the host also seat commands) and cannot undo; seated players may edit or remove empty seats, and new seats from `player` must be empty. `removePlayer` requires ownership, an empty seat or host authority on the server, releases held pieces onto the table at the seat, and clears undo history. Active and last seats can be removed: clear a stale actor, reset an empty turn order to zero, and disable hand UI/actions whenever there is no active seat.
- Stack drops, multi-draws, hand reordering and releasing onto a stack are validated atomically by the shared command engine. Hand order uses the existing instance `order` field; validate a complete hand and active actor before reordering. Camera is local presentation state. Per-seat hand preferences (face up on entry, table-hand visibility, seat lock) live on the player and change only via `handSettings` from that seat's active player; table-hand visibility is not a multiplayer privacy control.
- Tabletop layering follows instance-array order (boards render underneath); the `front` command persists it. Duplicating stacks, extracting pieces, multi-card hand drops and deterministic seeded dice rolls are shared commands, not client-only mutations. Copies retain stack membership via fresh stack IDs. A stack's optional `stackReversed` flag changes its visible top and faces without rewriting member order or face state; materialize those semantics when removing or merging pieces. Dice rolls change rows, not rotations or instance IDs.
- Never check secrets, local identities, authentication tokens, or generated test output into source control.

## Changes and documentation

Make focused changes, preserve existing workflows, and add or update targeted tests for behavior changes. Update the [README](README.md) when user-facing workflows, setup, persistence, multiplayer, commands, or their limitations change. Keep agent-specific architecture, validation, and trust guidance in this file rather than duplicating it in the Claude or custom-agent files.

After making and validating changes, commit them. Split distinct changes into separate, focused commits. Never commit secrets, local identities, or generated output.
